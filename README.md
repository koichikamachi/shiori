## 何が問題なのか

手続の前で人が止まるのは、情報が足りないからではない。インターネットには相続の記事があふれている。それでも人は止まる。理由は三つある。

**順番が分からない。** 記事はやることを並べるが、どれとどれがつながっているかを書かない。戸籍を集め終わるまで、財産の分け方の話し合いは一歩も進まない。

**どこを踏むと戻れないかが見えない。** 葬儀の費用を故人の口座から出す。ごく自然な行為である。しかしそれをすると、あとから多額の借金が判明しても相続を放棄できなくなることがある。

**最後は必ず「専門家にご相談ください」で終わる。** 何を相談すればよいか分からないから困っているのに、である。

そして、いくつもの立場が丸ごと抜け落ちている。**親に切り出せない子。負債があるかもしれない人。海外に資産がある人。そして、暮らしは足りているが、預金を子に多く残したいと思っている人。**

## 設計の核（三つ）

### 1　手続の判断に、生成AIを使わない

順序も、不可逆点も、期限も、Pythonの決定論的な計算が出す。法律の手続で間違った案内をすると実害が出るからである。

生成AIが担うのは、**地図そのものを最新に保つ仕事**（制度追従エージェント）と、**言葉づかい**（家族への文面、専門家への相談メモ）だけである。

### 2　金額も氏名も口座番号も受け取らない

入力欄そのものがない。受け取るのは「配偶者がいる」「事業がある」といった事情のタグと、「これは済んだ」という印、そして期限を数えるための経過日数だけ。**データベースを持たない。**

本人のしおりと遺族のしおりは通信しない。引き継がれるのは紙一枚である。

### 3　自律は「地図を最新に保つ」ほうに置く

制度は動く。エージェントが公的機関のサイトを自ら調べ、「この記述は古い」「根拠はこのURL」という**修正案を出す**。反映するかどうかは人が決める。エージェントはJSONを書き換える道具を持たない。

すでに一度、実際に起きた。事業承継税制の期限を調べたところ、計画の提出期限は延長されていたが、**実際に株を渡す期限は動いていなかった。** 古い情報のままなら、まだ間に合う人に「もう手遅れです」と案内するところだった。

## 動かしてみる

```bash
pip install -r requirements.txt

python -m src.main --list                        # 用意した16の状況
python -m src.main -s surv-day1                  # 遺族・死の直後
python -m src.main -s self-no-child              # 本人・子がいない
python -m src.main -s surv-rank-shift --brief    # 順位が繰り上がって相続人になった
python -m src.main --questions                   # 1日目に聞くこと
python -m src.main -s surv-day1 --map            # 地図の面（全体を見る）

python tools/render_map_svg.py -s all            # 地図を絵にする（HTML）
python tools/deadline_table.py                   # 期限の表（専門家に渡す一枚）
python tools/lint_nodes.py                       # 地図の点検
python -m pytest tests/ -q                       # テスト
```

Python 3.10 以上。外部サービスへの接続は不要である。

### 見どころ

**`surv-day10-memo` と `surv-day10-nomemo` を見比べる。** 本人が銀行名を一行書いてあるかどうかで、遺族の経路が丸ごと消える。

**`self-surplus`。** 元気な70歳。使わない預金を子に多く残したい。生前に渡す方法は**足し戻される期間がこれから年々のびていく**ので、早く始めた分しか効かない。保険の非課税枠は**健康なうちしか使えない**。商品名は一つも書かない。

**`surv-rank-shift`。** 死後100日、しかし相続人になったと知ったのは10日前。放棄の3か月は**そこから**始まる。死亡日で数えると「8日過ぎています」、知った時から数えると「82日あります」。同じ死である。

## 正しさを、どう保つか

この領域では、間違った案内が実害になる。だから**間違いを人ではなく機械が落とす**配置にした。

| | 中身 |
|---|---|
| `tools/lint_nodes.py` | 存在しないノードの参照、循環、未定義の条件、検証状態の食い違い、消えた道の説明もれ |
| テスト254本 | 「本人のメモがあると遺族の道が短くなるか」「期限が近ければ前提が未了でも警告するか」など、設計の急所を固定 |
| わざと壊して確かめる | テストを書いたら意図的にコードを壊し、捕まるかを見る。実際に一度、素通りした穴が見つかった |
| `verification_status` の四段 | 下書き／自分で調べた／一次資料で確認／**外部の専門家が確認**。確かめていないものに確認日を入れるとLintで落ちる |

**確かめていないものを、確かめたように見せない。** `EXPERT_VERIFIED` は、資格を持つ専門家が外部の立場で確認した場合にだけ使う。作った本人の読み返しはこれに当たらない。**現在0件である。** 画面にもそう表示する。

そのうえで、**事実を断定するノード（赤い帯を出すもの、期限を持つもの）17件は、一件ずつ人が読んだ。** そのうち10件は、e-Gov法令検索・法務省・国税庁・財務省・中小企業庁の一次資料まで当たって `SOURCE_VERIFIED` にしてある。読んだ記録は `in_house_reviewed_at` に置き、画面には出さない。

あわせて、**赤い帯（事実の断定）を出すノードには相談先を必ず置く**（無ければLintで落ちる）。制度の事実は断定するが、その人の事案の結論は断定しない。この線はS03のルール15に書いてある。

## いま、できていないこと

正直に書く。**この時点では、まだ応募要件を満たしていない。**

- Cloud Run へのデプロイ（必須要件①）
- Gemini API / ADK の接続（必須要件②）— 鍵の要らない部分（出力の型・7つの関門・テスト）は完成
- 画面（いまはターミナルで動く）
- 制度追従エージェントの本体

手元にあるのは「よくできた設計と、動く計算機」である。
