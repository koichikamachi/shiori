## 3　審査基準

原文の三つである。

1. **課題の新規性と解決策の有効性** — 「多くの人が抱えながらも、いまだ解決策が給されていない課題を発見できているか」  
2. **自律性・エージェントらしさ** — 「単純な自動化を超え、状況を判断しながら自律的に動作するエージェントか」  
3. **実装品質と拡張性** — 「アイデアをどれだけ高い品質で実現し、拡張性・運用性を考慮できているか」

### 賞

最優秀賞 50万円（1件）／優秀賞 25万円×3／特別賞 5万円×6／奨励賞 4万円相当×5

### 基準①について — ここは強い

S01 の第二部（九つの壁）が、そのまま「まだ解決策が与えられていない課題の発見」の記述である。とくに次の三つは、既存のサービスがまるごと落としている。

- **壁4（切り出せない）** — 母数が最も大きい立場に、既存のものは何も渡していない  
- **壁8（負債）** — 相続をプラスの財産を分ける話としてしか扱っていない  
- **壁9（海外）** — 日本の記事は扱わず、日本の専門家も「現地へ」で終わる

### 基準③について — 弱点をすでに手当てしてある

「運用性」がこの領域の最大の弱点である。制度が動くからである。`verification_status` の四段と `needs_check` 66件、`absolute_date` に対する lint の縛りは、その弱点への答えとして説明できる。

### 基準②について — **ここが一番の危険である**

次節で扱う。

## 4　設計上の緊張、その二つ

`S01` の第四部と同じ形式で扱う。

### 緊張A　「手元で完結する」と「Google Cloud にデプロイする」

要件は「Google Cloud へのデプロイをお願いいたします」であり、デプロイしたURLの記載が必須である。一方 `S02` の第一部2にはこう書いてある。

> 入力したことは外部のサーバーやクラウドへ送られず、私の手元のなかだけで処理される。

**この一文は、そのままでは守れない。** 判定をサーバーでするなら、事情のタグは一度サーバーへ渡る。

#### 解 —— 「送られない」ではなく「保存されない」に改める

守るべきものを取り違えないことである。使う人が恐れているのは、**財産の中身が他人の手元に残ること**であって、通信そのものではない。だから約束を、守れて意味のある形に置き換える。

| 変える前 | 変えたあと |
| :---- | :---- |
| 外部のサーバーへ送られない | **外部のサーバーに保存されない。データベースを持たない** |
| （記述なし） | **金額・氏名・口座番号・住所は、入力欄そのものが存在しない** |
| （記述なし） | 送るのは「配偶者がいる」「事業がある」といった事情のタグと、「済んだ」という印のIDだけ |
| （記述なし） | 印はブラウザのなかに置く。端末を変えれば消える（だから `S02` 第一部14の書き出しがある） |

これは弱めた約束ではない。**「アカウントがない。データベースがない。保存するものがない」は、それ自体が言い切れる強さを持つ。** そして嘘がない。

`S02` の第一部2と第四部3の文言を、この形に直す必要がある。憲法の修正であるから、勝手に直さず、判断を仰ぐ。

なお、より強く守る道もある。判定エンジンをブラウザ側で動かせば、タグは一度も外に出ない。しかし Python のエンジンとテスト33本を JavaScript に移すことになり、6週間の使い方としては割に合わないと考える。**Cloud Run はステートレス、状態はブラウザ、これで十分に誠実である。**

### 緊張B　「決定論」と「エージェントらしさ」

**これが勝敗を分ける。**

しおりの中心は「手続の順序と不可逆の判定は、プログラムが100%決定論的に行う。Gemini は言葉づかいに専念する」である。ハルシネーションを防ぐための正しい設計である。

しかし審査基準②はこうである。

> 単純な自動化を超え、状況を判断しながら自律的に動作するエージェントか

**決定論的なDAGは、字面のうえでは「単純な自動化」に見える。** そして「Geminiが文面をやわらかくする」だけでは、エージェントとは見なされにくい。ここで落ちる恐れがある。

#### 誤った解き方

手続の判断をGeminiに任せて「自律的」に見せること。これは `S01` 第四部の全部を捨てることになる。やらない。

#### 正しい解き方 —— 自律性を、判断ではなく「調べること」に置く

`S02` の第四部3にすでに答えがある。

> 外へ取りに行くのは公開されている情報だけである。取りに行くのであって、私のことが出ていくのではない。

**エージェントが自律的にやるのは、手続の判断ではない。地図そのものを最新に保つことである。**

具体的に三つ。

**(1) 制度改正の追従エージェント（本命）**

`needs_check` 66件を入力として、公的機関のサイトを自分で検索・読解し、次を出す。

- いまの制度と、ノードに書いてある内容が食い違っていないか  
- 食い違っていれば、どの項目をどう直すべきかの案  
- `verification_status` を `SELF_REVIEWED` から `SOURCE_VERIFIED` へ上げる根拠（URLと確認日）

**そして、これはすでに一度起きている。** 2026年8月31日、事業承継税制の期限を調べたところ、

- 特例承継計画の提出期限は令和8年3月31日 → **令和9年9月30日**に延長されていた  
- しかし、実際に株を渡す期限（令和9年12月31日）は**動いていなかった**  
- つまり急所は「計画の提出が間に合うか」ではなく「**渡すほうが間に合うか**」であり、あいだは3か月しかない

古い記憶のままなら「期限は過ぎました」と案内していた。間に合う人に「もう手遅れです」と言うところだった。**これがそのままデモになる。**

このエージェントは、審査基準の三つすべてに効く。②は自律性そのもの。③の「運用性」は制度が動く領域の最大の弱点であり、そこを埋める。①も、既存の終活サービスが誰も手当てしていない箇所である。

**(2) 地域の窓口を調べるエージェント**

`S02` の第四部1で「全国1,700自治体を維持するのは無理だから、用意できている町だけ見せて、それ以外は正直にそう言う」と決めた。エージェントなら、**聞かれたその町だけを、そのとき調べに行ける。** 全国分を抱えなくてよい。この設計とエージェントは、相性がよい。

**(3) 専門家への相談文を組み立てるエージェント**

現在地・条件・詰まっている理由から、誰に何を聞くかの文面を作る。ここは Gemini の従来の使い方である。

#### 実装のかたち

(1) と (2) は、ツールを持たせて自分で調べに行かせる必要がある。**ADK（Agent Development Kit）の出番である。** 検索と読解、そして「直す案を出す」までを回す。必須要件②も、これで ADK と Gemini API の両方を満たす。

そして守るべき線を明記しておく。**エージェントが直せるのは `data/nodes/*.json` の案を出すところまでである。** そのままデータを書き換えさせない。lint と pytest 33本を通し、人が見て、はじめて反映する。地図をAIに書き換えさせたら、`S01` 第四部の決定論が崩れる。

## 6　9月5日（渋谷）までにやること

締切ではないので、完成を目指さない。**経路を一度通す**ことに絞る。

1. `git init` して初回コミット（10分）  
2. Google Cloud のプロジェクトを作る。エントリーで届く300ドルのクーポンを当てる（20分）  
3. Streamlit か FastAPI で、いまのエンジンを叩くだけの最小の画面を作る（60分）  
4. **Cloud Run にデプロイして、URLが出るところまで通す**（60分）  
5. Gemini API のキーを通し、文面が一つ出るのを確認する（30分）

これができていれば、9月5日は「詰まっている一点を人に聞く日」に使える。

### 会場で聞くべきこと

- Cloud Run で Streamlit を動かすときの詰まりどころ  
- ADK で「検索して読んで案を出す」を作る最短の形  
- Gemini API を Cloud Run から呼ぶときの鍵の扱い（Secret Manager など）  
- 審査基準②の「エージェントらしさ」を、決定論的なコアを持つ設計でどう示すか

最後の一つが一番聞く値打ちがある。**主催者側の人に、緊張Bの解き方が通るかどうかを直接確かめられる機会である。**
