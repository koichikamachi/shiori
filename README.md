## 一言でいうと

**手続を「順序」と「通り過ぎると戻れない地点」を持つ路線図として、先に構造化した。**
そのうえで、今日決めることを数件だけ渡す。**ただし地図は、最初から全部見える。**

そして、その地図が古くならないように、**制度追従エージェント（Gemini）が公的機関のページを自分で探して読み、照合し、根拠つきの修正案を出す。** 反映するかどうかは人が決める。

---

## 何が問題なのか

手続の前で人が止まるのは、情報が足りないからではない。インターネットには相続の記事があふれている。それでも人は止まる。理由は三つある。

**順番が分からない。** 記事はやることを並べるが、どれとどれがつながっているかを書かない。戸籍を集め終わるまで、財産の分け方の話し合いは一歩も進まない。

**どこを踏むと戻れないかが見えない。** 葬儀の費用を故人の口座から出す。ごく自然な行為である。しかしそれをすると、あとから多額の借金が判明しても相続を放棄できなくなることがある。

**最後は必ず「専門家にご相談ください」で終わる。** 何を相談すればよいか分からないから困っているのに、である。

そして、いくつもの立場が丸ごと抜け落ちている。**親に切り出せない子。負債があるかもしれない人。海外に資産がある人。頼れる家族がいない人。そして、暮らしは足りているが、預金を子に多く残したいと思っている人。**

## 設計の核（三つ）

### 1　手続の判断に、生成AIを使わない

順序も、不可逆点も、期限も、Pythonの決定論的な計算が出す。法律の手続で間違った案内をすると実害が出るからである。

生成AIが担うのは、**地図そのものを最新に保つ仕事**（制度追従エージェント）と、その照合結果を読む人に向けて書く**言葉づかい**だけである。

### 2　金額も氏名も口座番号も受け取らない

入力欄そのものがない。受け取るのは「配偶者がいる」「事業がある」といった事情のタグと、「これは済んだ」という印、そして期限を数えるための経過日数だけ。**データベースを持たない。**

本人のしおりと遺族のしおりは通信しない。引き継がれるのは紙一枚である。

### 3　自律は「地図を最新に保つ」ほうに置く

制度は動く。エージェントが公的機関のページを自ら探して読み、「この記述は古い」「根拠はこのURLのこの一文」という**修正案を出す**。反映するかどうかは人が決める。**エージェントは地図を書き換える道具を持たない。**

すでに一度、実際に起きた。事業承継税制の期限を調べたところ、計画の提出期限は延長されていたが、**実際に株を渡す期限は動いていなかった。** 古い情報のままなら、まだ間に合う人に「もう手遅れです」と案内するところだった。

## 制度追従エージェント

駅（ノード）ごとに、次の順で照合する。

1. **探す**（ExplorerRole）— Gemini と Google 検索で公的機関のページを探す。見つからなければ、その駅に登録してある公的URLに戻る。
2. **選り分ける**（EvaluatorRole）— 主題の外れたページを除き、曖昧な点に印をつける。
3. **読む**（ReaderRole）— 取得した本文から、地図の記述と突き合わせる一文を引く。
4. **関門を通す** — 人が見る前に、下の七つの関門で機械が落とす。
5. **人に渡す** — 結果と修正案を、「人の確認が必要」の印つきで出す。

画面では、この足取りが起きた順にそのまま流れる。ライブで照合できないときは、日付つきの過去の照合記録（`data/archive/`）を、**「記録」と明示して**見せる。キャッシュをライブの結果のように見せない。

### 七つの関門（`src/agent/guards.py`）

| | 関門 | 落とすもの |
|---|---|---|
| 1 | 公的機関か | https の .go.jp／.lg.jp 以外を根拠にしたもの |
| 2 | 本当に取得したか | 実際に取得していないページを根拠にしたもの |
| 3 | 日付は正しいか | 未来の日付のページ |
| 4 | 原文の引用か | 取得した本文に逐語で含まれない引用（NFKC 正規化・空白除去のうえ、10文字以上） |
| 5 | 根拠の数に見合った判定か | 根拠なしの「変わった／変わっていない」（不確かに格下げ）。根拠1件での確信度「高」 |
| 6 | 修正案の形は正しいか | 直してはいけない場所・型の変わる値・同じ値・根拠のない修正案。人以外が付ける EXPERT_VERIFIED |
| 7 | 今日の照合か | 照合日が今日でないもの。「人の確認が必要」の印が無いもの |

あわせて、駅の識別子を検査し、パスをたどる攻撃を防いでいる（`validate_node_id`）。

## 動かしてみる

```bash
pip install -r requirements.txt

python -m src.main --list                        # 用意した17の状況
python -m src.main -s surv-day1                  # 遺族・死の直後
python -m src.main -s self-no-child              # 本人・子がいない
python -m src.main -s surv-rank-shift --brief    # 順位が繰り上がって相続人になった
python -m src.main --questions                   # 1日目に聞くこと
python -m src.main -s surv-day1 --map            # 地図の面（全体を見る）

python tools/render_map_svg.py -s all            # 地図を絵にする（HTML）
python tools/deadline_table.py                   # 期限の表（専門家に渡す一枚）
python tools/make_printable.py                   # 持って行く紙を作る
python tools/lint_nodes.py                       # 地図の点検
python -m pytest -q                              # テスト
```

地図の計算は Python 3.10 以上で動き、外部サービスへの接続は要らない。

画面とエージェントを手元で動かすときは、次のようにする。

```bash
pip install -r requirements-web.txt
# GEMINI_API_KEY を環境変数に置く（.env も可。リポジトリには入れない）
python -m uvicorn server:app --port 8080
```

鍵が無くても地図は表示される。照合は、日付つきの記録を「記録」として見せる。

### 見どころ

**`surv-day10-memo` と `surv-day10-nomemo` を見比べる。** 本人が銀行名を一行書いてあるかどうかで、遺族の経路が丸ごと消える。

**`self-surplus`。** 元気な70歳。使わない預金を子に多く残したい。生前に渡す方法は**足し戻される期間がこれから年々のびていく**ので、早く始めた分しか効かない。保険の非課税枠は**健康なうちしか使えない**。商品名は一つも書かない。

**`surv-rank-shift`。** 死後100日、しかし相続人になったと知ったのは10日前。放棄の3か月は**そこから**始まる。死亡日で数えると「8日過ぎています」、知った時から数えると「82日あります」。同じ死である。

## 正しさを、どう保つか

この領域では、間違った案内が実害になる。だから**間違いを人ではなく機械が落とす**配置にした。

| | 中身 |
|---|---|
| `tools/lint_nodes.py` | 存在しないノードの参照、循環、未定義の条件、検証状態の食い違い、消えた道の説明もれ |
| テスト360本 | 「本人のメモがあると遺族の道が短くなるか」「期限が近ければ前提が未了でも警告するか」「関門が作り話の引用を落とすか」「鍵がリポジトリに入っていないか」など、設計の急所を固定 |
| わざと壊して確かめる | テストを書いたら意図的にコードを壊し、捕まるかを見る。実際に一度、素通りした穴が見つかった |
| `verification_status` の四段 | 下書き／自分で調べた／一次資料で確認／**外部の専門家が確認**。確かめていないものに確認日を入れるとLintで落ちる |

**確かめていないものを、確かめたように見せない。** `EXPERT_VERIFIED` は、資格を持つ専門家が外部の立場で確認した場合にだけ、人の手で付ける。作った本人の読み返しはこれに当たらない。**現在0件である。** 画面にもそう表示する。

いまの内訳は、78駅のうち **`SOURCE_VERIFIED` 17件**（e-Gov法令検索・法務省・国税庁・財務省・中小企業庁などの一次資料まで当たったもの）、**`SELF_REVIEWED` 61件**である。

あわせて、**赤い帯（事実の断定）を出すノードには相談先を必ず置く**（無ければLintで落ちる）。制度の事実は断定するが、その人の事案の結論は断定しない。この線はS03のルール15に書いてある。

---

## まだ、できていないこと

正直に書く。

- **専門家の確認は0件である。** `EXPERT_VERIFIED` を得る道筋は、これからつくる。
- **修正案は、確かめた度合いを上げる向きに偏っている。** 出典が変わったときに、確認済みを未確認に戻す（降格の）提案も出せるようにする。上げる向きだけでは、保守ではなく宣伝になるからである。
- 地図が覆うのは相続と死後の手続に限られる。介護・年金・事業承継税制など、ほかの手続への広げ方は検討中である。

## 構成

```
server.py           画面と照合の API（FastAPI。Cloud Run で動く形）
Dockerfile          Cloud Run に上げる形。何が入り、何で起動するかが一枚に書いてある
docs/   S01〜S10    設計文書。原本はここ。過去版は git が持っている
        NEXT_GEN_UI_SPEC  次期の画面の設計（現行のコードには影響しない）
data/
  nodes/            地図そのもの（本人45・家族5・遺族28）
  schema/           ノードの形と、使ってよい条件27種
  checks/           エージェントが確かめる123項目
  archive/          日付つきの照合記録（ライブで照合できないときに「記録」として見せる）
  proposals/        エージェントが出す修正案の置き場
src/
  engine/           expr（式の読み取り）state（状態5値）engine（判定）
  agent/            agent（探す・選る・読む・書く）tools（検索と取得）
                    guards（七つの関門）schema（出力の型）
  main.py           ターミナルで17の状況を再現する
tests/              エンジン・地図・相続人・関門・エージェント・サーバ・鍵の見張り
tools/              lint_nodes・extract_checks・list_for_review・render_map_svg
                    deadline_table・make_printable・make_onepager・render_node_image
```

### 設計文書

| | 中身 |
|---|---|
| **S01** | 名前と位置づけ。九つの壁。既存サービスとの違い。作らないと決めたもの |
| **S02** | ユーザーから見た全体像。一人称で書いた「憲法」。ここに現れないものは作らない |
| **S03** | エンジンの決めごと（ルール1〜15）。実装はこれに従う |
| **S04** | 応募要件と、それが設計に与えた影響 |
| **S05** | 当日の質問 |
| **S06** | 説明文と、開発の宿題 |
| **S07** | 制度追従エージェントの設計 |
| **S08** | 目視で確かめる分（`tools/list_for_review.py` が生成する） |
| **S09** | 期限の表 |
| **S10** | Cloud Run に上げる手順 |
