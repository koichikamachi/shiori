質問1　審査基準②「エージェントらしさ」を、どう示せばよいか

★ 一番大事。時間切れになっても、これだけは聞く

背景（相手に伝えること）

審査基準②の原文はこうです。「状況を判断しながら自律的に行動するエージェントか。可観測性やセキュリティへの配慮。」

しかし私の設計では、手続の判断はあえて生成AIにさせていません。 決定論的なプログラムが決めます。ハルシネーションを防ぐためです。そうすると、字面のうえでは「単純な自動化」に見えてしまうのではないかと心配しています。

まず、後半の「可観測性」について、私の解釈を述べます

可観測性を、「このアプリが、自分の知らないことを自分で数えて、外に出せること」と解釈しました。

具体的にはこうです。手続75件のうち、公的機関の資料に当たって確かめたものと、まだ確かめていないものを、項目ごとに画面に出しています。 いま未確認は109件です。エージェントの出力は、LLMを使わないPythonの七つの関門が落とします。テストは281本あり、わざとコードを壊して、テストが気づくかを確かめるやり方で通しています。個人情報は保存しません。保存するものがないので、ログインも要りません。

とくに期限は別格に扱っています。 期限が付いている手続は75件のうち10件だけです。この10件は、一次資料に当たっていないとlintが通らないようにしました。画面には期限の隣に、どこで確かめたかと確認日を出します。

そのうえで、前半の「自律性」について

自律性を「手続の判断」ではなく「地図の保守」に置こうと考えています。

具体的には、手続データに「まだ確認の取れていない項目」が109件あります。これを入力として、エージェントが公的機関のサイトを自分で検索・読解し、「この記述は古い」「根拠はこのURL」「引用はこの一文」「確認日はこの日」という修正案を出します。データには直接書き込ませません。反映するかどうかは人が決めます。

答えは成功と失敗の二値ではなく、五つに分けています。現行のまま／古い／ページはあるがはっきり書いていない／公的なページが無い／根拠が要件を満たさなかった。 空振りを失敗として潰すと、エージェントは何かを見つけたふりをするからです。

実際に起きたこと三つ（これが説得材料である。順に出す）

① 期限がふたつあった。
事業承継税制（個人版）の期限を調べたところ、計画の提出期限は令和8年3月31日から令和10年9月30日に延長されていましたが、実際に事業用資産を渡す期限は令和10年12月31日で動いていませんでした。 ひとつなぎで読むと「延長された」で終わります。古い情報のままなら、まだ間に合う人に「もう手遅れです」と案内するところでした。
→ だから ADK の役のなかに、わざと反対から見る「崩す役」を独立させました。

② 一次資料どうしが食い違っていた。しかも、片方がまだ直っていないだけだった。
財務省の「令和8年度税制改正の大綱」は延長後の期限を書いていますが、国税庁のタックスアンサー No.4153 は、いまも令和8年3月31日のままです。 改正前の記載です。
→ つまりエージェントは「公的サイトに書いてあるか」を見るだけでは足りず、そのページ自身がいつのものかを日付で判定しなければならない。 出典の格ではなく、日付で勝負が決まる場面が現実にある。これは机の上では思いつかない要件でした。

③ URLがあることと、そのURLが主張を支えていることは、別だった。
私のデータは、補充遺贈（渡す相手が先に亡くなっていた場合の備え）の根拠として民法994条を挙げていました。しかし条文本文に当たると、994条は「遺贈は効力を生じない」と言うだけで、備えを置ける根拠にはなりません。本当の根拠は995条のただし書きでした。 条文を逐語で突き合わせて初めて分かりました。
→ だから機械の関門に、「引用文が、取得したページに一字一句あるか」を入れています。もっともらしい要約は、ここで全部落ちます。

決定論のコアを壊さないための関門（LLMを使わない Python が落とす）

関門 落ちる条件
出どころ go.jp lg.jp 以外のドメインは根拠として認めない
引用の一致 引用文が取得ページに一字一句なければ、その根拠を捨てる
根拠ゼロ 残った根拠が0件なら「古い」と名乗れない。判定を下げる

これを21本のテストで縛っています。わざとコードを壊して、テストが気づくかを確かめるやり方で通しました。

聞きたいこと

この立て方で、審査基準②を満たすと見なされるでしょうか。とくに「可観測性」の解釈が、意図されているものと合っているかを知りたいです。

答えやすいように、選択肢を用意しておく

(b) 弱い。ユーザーとの対話のなかで自律的に動く部分も要る
(c) 見せ方の問題。同じ実装でも、説明の仕方で印象が変わる
(d) 可観測性の解釈が違う（→ 何を指しているのか教えてください）
(e) その他

(b) だったら、続けて聞くこと

決定論的なコアを壊さずに、対話のなかに自律性を入れるとしたら、どのあたりが自然でしょうか。私が思いつくのは「聞き方を決める役」です。質問の答えではなく、次に何を尋ねるかをエージェントに選ばせる。 答えの解釈は決定論に渡す。これは筋が通っているでしょうか。

質問3　地図の面を、Cloud Run のうえでどう出すか

背景（相手に伝えること）

このアプリの中心は「今日やること三件」ではなく、全体が一枚で見えることです。横浜から新百合ヶ丘まで車で行くのに、一時間先までしか出ない地図は、地図ではありません。

いまは路線図をHTMLとして書き出しています。配置は決定論です。 力学的なレイアウトは使いません。同じ条件なら、いつも同じ場所に同じ駅が出ます。X軸は時間、Y軸は流れ（相続と承継／亡くなったあとの手続／事業の承継／国境をまたぐこと／家族に切り出す／引き継ぎ）です。

「まだ分からない」を灰色の霧として描くのが、この地図の勘所です。「いいえ」と「まだ答えていない」を混ぜると、初日の遺族に「遺産に不動産がないので名義変更は要りません」と断定してしまう。 混ぜてはいけない。

前夜に、(b) と (c) を混ぜた形で出しました。もう動いています。

FastAPI が、その場で判定エンジンを回して路線図を組んで返します。状態はURLに持たせます（/map/surv-day80?today=2026-09-05）。サーバは何も覚えません。セッションもCookieもありません。
同じURLを二度開けば、同じ地図が出ます。 決定論のコアが、クラウドのうえでも同じ答えを出すことを、URLそのものが示せると考えました。

このアプリの記述は、私と生成AIが書いています。どちらも間違えます。資格のある専門家の点検を、工程のどこに置くべきかを考えています。

いまの案は、「言い切りの強さは、確かめの強さを超えない」という規則を置くことです。まだ確かめていない項目は灰色の説明にとどめ、一次資料で確かめたら制度の事実として書き、専門家の点検を経てはじめて赤い帯に出す。点検は「出すための条件」ではなく「強く言うための許可」にしておけば、返事待ちで開発が止まりません。

そのうえで、まず期限10件だけを一枚にして出そうとしています（docs/S09_期限の表.md）。75件を渡せば読まれないが、10行なら読まれると考えました。

断定を避ける文言と、審査の印象

弁護士でない者・税理士でない者が、法律行為についての意見を述べ、税務相談に答えることは禁じられています。ですから制度の事実は断定し、その人の事案の結論は断定しないという線を引いています。「あなたは相続人です」「放棄すべきです」「相続税がかかります」とは書きません。
