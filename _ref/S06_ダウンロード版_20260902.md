# しおり — 説明文と、そこから出てくる開発の宿題

**S06\_説明文と開発の宿題** 2026年9月2日　BKW研究所 配置先　`docs/S06_説明文と開発の宿題.md`

---

## 0　この文書の使い方

説明文は、書くものではなく**決めるもの**である。

三つの審査基準に答えようとすると、答えられない欄が出る。**その空欄が、そのまま開発の宿題になる。** 逆に、作ってから言葉にしようとすると、基準②が空欄のまま提出することになる。

だから順序はこうする。

説明文の骨格を決める → 空欄が見える → 空欄を埋めるために作る → 動画で見せる

本書のなかで、

- **【書ける】** … いま動いているので、そのまま提出できる  
- **【まだ書けない】** … 作らないと嘘になる。これが開発の宿題である

## 2　説明文の骨格 — 三つの基準に、一つずつ

審査基準は三つである。**説明文は、この三つに一つずつ答える形にする。** S01・S02の要約ではない。

| 基準 | 何で答えるか | 状態 |
| :---- | :---- | :---- |
| ① 課題の新規性と解決策の有効性 | 九つの壁。とくに壁4（切り出せない）・壁8（負債）・壁9（海外） | **【書ける】** |
| ② 自律性・エージェントらしさ | 制度追従エージェント。事業承継税制の一件が実例 | **【まだ書けない】** |
| ③ 実装品質と拡張性 | 決定論的なコア、Lintと36テスト、`verification_status` の四段 | **【書ける】** |

**②だけが空欄である。** そして②は、三つのなかで一番落ちやすい基準である。

## 3　説明文の草稿

そのまま貼れる形で書く。ダッシュボードの「プロジェクト紹介」に入れる想定。実際の入力欄を見てから、長さを詰める。

### 誰のためのものか

相続と、亡くなったあとの手続の前で立ち止まっている人のためのものです。

三つの立場があります。**自分の万一に備える本人**、**親のことが気になっているが切り出せない家族**、そして**すでに遺された人**です。

本人といっても一人ではありません。年金で暮らす人、代々の土地を持つ人、会社を持つ人、海外に口座がある人、そして借入と保証がある人。**それぞれで、今日打つべき一手がまったく違います。**

### 何が問題なのか

**手続の前で人が止まるのは、情報が足りないからではありません。**

インターネットには相続の記事があふれています。それでも人は止まります。理由は三つです。

**順番が分からない。** 記事はやることを並べますが、どれとどれがつながっているかを書きません。戸籍を集め終わるまで、財産の分け方の話し合いは一歩も進まない。この前後関係が見えないので、読み終えても何から手をつけてよいか分かりません。

**どこを踏むと戻れないかが見えない。** 葬儀の費用を故人の口座から出す。ごく自然な行為です。しかしそれをすると、あとから多額の借金が判明しても相続を放棄できなくなることがあります。**知らないうちに、選べたはずの道が消えます。**

**そして、最後は必ず「専門家にご相談ください」で終わる。** 何を相談すればよいか分からないから困っているのに、です。

既存の終活サービスは、この三つのどれにも答えていません。あれは**保管庫**です。書いたものを預かりますが、いつ何をするかは教えません。

さらに、三つの立場が丸ごと抜け落ちています。

- **親に切り出せない子。** 使う気はあるのに、相手に話を持ち出せない。母数が最も大きい立場ですが、既存のものは何も渡していません。  
- **負債があるかもしれない人。** 相続をプラスの財産を分ける話としてしか扱っていません。保証債務は、主債務者が払っているあいだ何も届かないので、気づいたときには期限が過ぎています。  
- **海外に資産がある人。** 日本の記事は扱わず、日本の専門家に聞いても「現地の弁護士へ」で終わります。最大の危険は税額でも手続の複雑さでもなく、**遺族がその財産の存在に気づかないまま終わること**です。

### 何を作ったか

**手続を、順序と「通り過ぎると戻れない地点」を持つ地図として、先に構造化しました。**

いま64件のノードがあります。それぞれが、前提となる手続、待ちの理由、不可逆かどうか、期限、そして「誰に何を持って相談するか」を持っています。この地図は、公認会計士としての実務の知見を、そのままデータにしたものです。

使う人からは、**金額も氏名も口座番号も受け取りません。** 入力欄そのものがありません。受け取るのは「配偶者がいる」「事業がある」といった事情のタグと、「これは済んだ」という印だけです。サーバーには何も保存しません。データベースを持ちません。

そのうえで、決定論的な計算が三つを出します。

- **今日、あなたが決めること**（三件を超えません）  
- **今は待ってよい理由**（「役所の回答待ちです。あなたの落ち度ではありません」）  
- **触る前に知っておくこと**（赤い帯。事実を断定し、直後に逃げ道を置きます）

**手続の判断に、生成AIは一切使っていません。** 法律の手続で間違った案内をすると実害が出るからです。

### 本人の一手が、遺族の道を消す

しおりの中心は、ここにあります。

本人が「取引のある銀行の名前」を紙に一行書く。それだけで、遺族が通帳を探し、郵便物を待ち、心当たりに照会して回る数か月が、まるごと消えます。

**しかも、本人のアプリと遺族のアプリは通信しません。** 引き継がれるのは紙一枚です。遺族が自分の端末で新規に始め、「本人が残した紙は見つかりましたか」という問いに答えると、探索の経路がそこで消えます。

だからしおりは、その紙の中身を知りません。知らないまま、道筋だけを変えます。**個人情報を預からないことは、機能の制限ではなく、設計の中心です。**

そして、何も残されていなかった場合が**標準の経路**です。本人の準備を前提にすると、使える人がごく一部になってしまうからです。

### 【まだ書けない】制度に追いつき続けること

*※ ここは9月中に作る。作ってから書く。*

（骨子）制度は動きます。手続データには、まだ専門家の確認を受けていない項目が66件あります。これをエージェントが自ら公的機関のサイトで調べ、「この記述は古い」「根拠はこのURL」「確認日はこの日」という修正案を出します。反映するかどうかは人が決め、Lintと36本のテストを通してから取り込みます。

すでに一度、実際に起きました。事業承継税制の期限を調べたところ、計画の提出期限は延長されていましたが、**実際に株を渡す期限は動いていませんでした。** 古い情報のままなら、まだ間に合う人に「もう手遅れです」と案内するところでした。

### どうやって正しさを保つか

この領域では、間違った案内が実害になります。だから、間違いを人ではなく機械が落とす配置にしました。

- **`lint_nodes.py`** — 存在しないノードの参照、循環、未定義の条件、検証状態の食い違いを機械的に落とします  
- **36本のテスト** — 「本人のメモがあるとき遺族の道が短くなるか」「期限が近ければ前提が未了でも警告を出すか」など、設計の急所を固定しています  
- **わざと壊して確かめる** — テストを書いたら、意図的にコードを壊して捕まるかを試します。実際に一度、テストが素通りした穴が見つかりました  
- **`verification_status` の四段** — 下書き／自分で調べた／一次資料で確認／専門家が確認。確かめていないものに確認日を入れると、Lintで落ちます

**確かめていないものを、確かめたように見せません。** 現在64件のうち62件が「専門家の確認を受けていない」状態であり、画面にもそう表示します。

## 4　【まだ書けない】を埋めるための、開発の宿題

説明文で空欄になったところが、そのまま優先順位になる。

### 宿題1　制度追従エージェント（ADK＋Gemini）★最優先

**基準②への答えであり、必須要件②も同時に満たす。**

| 作るもの | 中身 |
| :---- | :---- |
| 入力 | `needs_check` の66件（テキスト） |
| 動き | 公的機関のサイトを検索 → 読む → 現在の記述と突き合わせる |
| 出力 | `{古いか／根拠URL／確認日／直す案}` の構造化データ |
| 縛り | **JSONを直接書き換えない。案を出すところまで** |
| 失敗の扱い | 「見つからない／日付不明／曖昧」を成功・失敗の二値にしない |

**動画で見せる場面：** 事業承継税制のノードを選び、エージェントを走らせ、「期限が延びている」という修正案が出てくるところ。

### 宿題2　語り部（Gemini API）

計算結果を受け取って、家族への文面と専門家への相談メモを作る。**判断はさせない。言葉づかいだけ。**

### 宿題3　画面（Streamlit など）

`src/main.py` がすでに出しているものを、そのまま画面に流す。**新しい判断を画面側に書かない。**

必要なのは四つだけ。赤い帯／今日の三件／待っている理由／消えた道。

### 宿題4　Cloud Run へのデプロイ

**必須要件①。** 状態はブラウザに置き、サーバーは何も保存しない。

### この順番である理由

宿題1が基準②の答えなので、**画面より先に作る。** 画面が先だと「見栄えはよいが基準②が空欄」という、一番負けやすい形になる。

## 5　動画3分の割り付け（先に決めておく）

**動画の台本を先に決めると、画面に何が要るかが決まる。** 逆にすると、映らない機能を作ることになる。

| 時間 | 何を映すか | 必要なもの |
| :---- | :---- | :---- |
| 0:00–0:25 | 死の直後の画面。赤い帯と「今日はこの三件だけ」 | 画面（宿題3） |
| 0:25–0:50 | 「今日はやらなくてよいこと13件」「待っているのは役所の回答です」 | 画面 |
| 0:50–1:25 | **本人の画面で銀行名を一行チェック → 遺族の画面に戻ると、探索の経路が消える** | 画面 |
| 1:25–2:05 | **制度追従エージェントを走らせる。事業承継税制の修正案が出る** | 宿題1 |
| 2:05–2:35 | Lintとpytestが緑になる画面。`verification_status` の表示 | できている |
| 2:35–3:00 | 一行でまとめる | — |

**0:50–1:25 と 1:25–2:05 が山場である。** ここが映らなければ、動画を撮る意味がない。だから宿題1と宿題3は、この二つの場面が映ることだけを目標に作る。

**それ以外の機能は、10月15日までに要らない。**

## 6　次にやること

1. ダッシュボードの「プロジェクト紹介」タブを開き、**入力欄の種類と字数制限を確かめる**（草稿の長さを合わせるため）  
2. 上の草稿を、その欄に合わせて詰める  
3. 宿題1（制度追従エージェント）の設計に入る

なお、**説明文は提出締切まで何度でも直せる。** 完成させてから入れるのではなく、**いまの草稿を先に入れてしまい、開発が進むたびに書き足す**のが安全である。空欄のまま10月を迎えるのが一番危ない。
